# 规范写作（standard-authoring）

> Provenance：蒸馏自 dotnet-deepseek-harness-desktop `docs/coding-standards.md`/`architecture-standards.md` 的写作模式（MIT，2026-09-05）。元规则与实例分离：C#/Ryn 具体规则不搬，搬"怎么写规范"。

## 1. 强制力度分档（每条规范必须声明落在哪档）

| 档 | 机制 | 例子 |
|---|---|---|
| **机器拦** | verify-*/CI 门禁，违约 fail loud | ADR 格式、字数预算、死链 |
| **构建/工具警告** | linter/analyzer warning，保持零警告 | 风格规则、契约扫描 |
| **IDE 提示** | 编辑器提示，不阻断 | 惯用偏好 |
| **留评审** | 机器无法强制 → 列「AI 兜底」清单（见 [review.md](review.md) §5） | 命名语义、架构意图 |

规则：**能升档就升档**（自动化成熟一条升一条）；声明档位时写清"为什么停在这档"（如"需语义分析，只能留评审"）——这本身就是可复审的决定。

## 2. 标准与现状分离

- `architecture-standards`（规范，怎么被组织）与 `architecture`（现状地图）是**两份文档**：混写会导致规范被现状拖改。
- 规范条目用**编号**（R1、R2…）与**判别式写法**（可判定"是否违反"，不是"建议考虑"），例如"组合根只装配"比"组合根应尽量简单"可审。

## 3. 结构模板

1. **强制力度**节（§1 分档表）。
2. **关键约定**（摘要，每条 1-3 行，细则有家的链接过去）。
3. **行为契约**节：跨切面行为约定（错误处理/生命周期/边界）的单一事实源；机器盖不住的条目显式标注"留评审"。
4. **健康闸**（如有）：尺寸/复杂度阈值 + "先拆再上"（diff 不得把文件顶过阈值；触碰已超阈值文件须先拆到阈值内）。

## 4. 元纪律

- 规范正文 ≤ 预算（manifest 管）；细则超出预算即另立家（cookbook/method 对应篇）并链接。
- 每条规范可回答"违反了会怎样"（哪个门禁/哪条评审项）——回答不了的，先过理念四骨（[ai-collaboration-method.md](ai-collaboration-method.md) §一.3），过不了就别立。
