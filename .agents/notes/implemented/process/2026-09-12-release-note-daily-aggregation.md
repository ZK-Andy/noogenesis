# Agent Note: release-note 末节按提交日归并（跨大批次正文去过程清单）

Status: implemented

Review: FULL/2026-09-12/pending（三重审核进行中，收口时回填真实结论）

## Problem

- 末节（其他变更 / Chores）承接 docs/chore/test 等过程类条目，而本仓一个功能批次带多笔过程提交（收尾落账、评审收口各一笔）；批次一多，末节就压过正文：`v0.2.3..dsh-v0.2.4` 跨 59 笔时 47 条、`dsh-v0.2.4..dsh-v0.2.5` 跨 67 笔时 42 条（[release-shape-alignment](2026-09-09-release-shape-alignment.md) 两次实发节；实发样本 n=2，标【探索性】）。
- 两次都靠发布者手工按批次归并（首验成 3 条、二次成 5 条）：脚本输出与可发布正文之间存在一段无工具支撑的手工工段，归并口径只在发布者当场判断里，不可复现。
- 「批次」边界无法由提交元数据机械还原（实测：收尾/收口标记切段得 39–41 段、30 分钟空档得 7 段、自然日得 3 段，发布者按主题归并的是 3–5 条）：主题归并是编辑判断，把它的近似写成机械判据只会换一个不可信的边界。

## Decision

**末节按提交日归并成「每日一条」，条目零丢弃**（`scripts/release/release-note.mts`）。

1. 分组键 = committer date short（`git log --format=%cs`）：提交对象内记录的时区口径，输出与运行机器/时区无关；日志顺序新→旧，同日条目必然相邻，一趟扫描即成桶。
2. 日桶形态 = `- **<日期>（N 笔）**：<说明>；<说明>… @作者`（英文侧 `**<日期> (N entries)**: ` + `; ` 连接）：N 即桶内条数，归并不删条目；细节由正文尾行 Full Changelog 承接（[release-flow](../../../workflows/release-flow.md) 的「未知类型落末节、不静默丢条目」纪律不变）。
3. 逐条项与归并项共用同一输出项形态（说明 + 作者集合）：逐条项为单作者，归并项为日桶内去重作者——多人仓由此保住归属且不逐条重复标注。
4. 作用面只有末节：新增功能/体验优化/问题修复是用户可见面，保持逐条（对齐上游形态）。
5. 首节锚点 id、双语镜像、`EN_POLISH_HINT` 润色提示、`chore(release)` 自身跳过、Full Changelog 推导均不变。

## Alternatives considered

- **机械还原「批次」边界**（收尾/收口标记切段或时间空档切段）——落败：实测不可还原（见 Problem 第三点），正则调参换不来稳定边界，反而把编辑判断伪装成机械判据。
- **末节折叠成一行**（计数 + Full Changelog 指针）——落败：正文最省，但把可发布的实质条目（如技能 provider 取证落档）一并折叠，发布者须回 `git log` 重新找料，手工工段只是挪位。
- **按 scope 或关键词主题聚合**——落败：scope 是仓内自用词（`docs(handoff,journal)`），对外正文读者不可解；关键词聚类不可复现，判据无从自证。
- **加档位开关**（默认逐条 / `--group` 归并）——落败：两套形态是无必要兼容层，逐条形态用 `git log` 即可取，不为不会发生的回退留开关（[anti-overdesign](../../../../docs/method/anti-overdesign.md) 范围契约）。
- **给本件加 `--self-test` 夹具并登记 `gates.json`**——不采纳：release 工具族的证据形态 = 真实历史区间实跑（见下节），归并是纯字符串整形，判据面由评审精读 + 区间实跑的计数不变式盖住；为一个发版侧工具单立门禁条目不成比例。

## Consequences

- 末节行数与条目数解耦：日桶数 ≤ 提交覆盖天数，跨大批次时正文不再被过程清单淹没（0.2.5 区间实测 42 条 → 3 条）。
- 发布者不再需要重画批次边界：脚本直接给按日成组的骨架，发布者在桶内做主题取舍与润色（[release-flow](../../../workflows/release-flow.md) 步骤 4 的「脚本生成骨架 + 发布者润色」分工不变）。
- 日桶仍可能是长段落（0.2.5 单桶 23 条）——脚本保底的是「不丢条目、不淹行数」，主题化始终是发布者判断。
- 日界随 committer date：改写提交历史（amend/rebase）会移动日界；跨时区协作时同一天的提交可能落到相邻桶（提交对象内记录时区优先于本机时区）。
